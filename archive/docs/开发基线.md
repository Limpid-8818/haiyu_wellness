## 3. 逐项冲突与解释

### 3.1 角色模型冲突：四角色 MVP 与早期机构角色

较新的交接文档和当前源码按 `public`（仅 Agent 场景）、`guest`、`staff`、`dean` 组织。SQLite 的 `users.role` 只有 `guest`、`staff`、`dean`；工作人员页面是一个通用工作台，院长另有管理页面。

早期选题书、RTM 和部分概要设计文字把机构端拆为医护人员、管理员、康养服务人员（教练、理疗师、配餐员），并要求医护审核台、服务人员日程、管理员权限矩阵。现有源码没有这些独立登录角色、岗位字段或机构端模块。因此“工作人员”不能在文档中直接等同于“医护/管理员/服务人员”，早期角色只作为后续扩展需求保留。

### 3.2 持久化冲突：旧内存/快照描述与当前关系型 SQLite

`项目依据/01-project-design.md`、`02-database-design.md` 和 `03-api-contract.md` 描述的是内存对象或 `app_state` 快照、状态变更后写快照、再迁移 PostgreSQL 的早期原型；旧 API 也按该模型列出 `plans`、`reservations`、`metrics` 等实体。

当前代码已不是该内存快照：`server/src/db.js` 直接创建关系型 SQLite 表（`users`、`guest_profiles`、`health_records`、`medical_advice`、`news`、`audit_logs`、`staff_reviews`、`assistant_messages`、`health_intakes`），开启 WAL 和外键，并以 `DB_PATH` 选择文件。当前 SQLite 表仍不包含 MySQL 目标中的 `staff_guest_assignments`、`assistant_sessions` 等完整结构，不能把“关系型 SQLite 已有”误写成“已完成正式迁移”。

### 3.3 数据库目标冲突：PostgreSQL 旧目标与 MySQL 8.0 最新目标

早期六份 Markdown 和 2026-09-19 概要设计的数据库章节/部署表写的是 PostgreSQL；概要设计 Word 与 PDF 的对应内容一致，但这是设计材料中的旧目标。2026-09-22 交接文档、`haiyu_wellness_mysql8.sql` 和 2026-09-20 Excel 数据字典明确采用 MySQL 8.0，且增加了资源分配、Agent 会话、审核字段和索引设计。

本轮口径为：当前运行 SQLite；下一数据库阶段以 MySQL 8.0 SQL/字典为迁移目标；PostgreSQL 只作为历史设计记录，不作为当前实施目标。迁移前仍需完成适配层、迁移/回滚、数据校验、备份恢复和权限并发验证。

### 3.4 鉴权头冲突：旧 `x-token` 与当前 Bearer

早期 `项目依据/03-api-contract.md` 描述 `x-token`，并计划替换为短时 access token + HttpOnly refresh cookie。当前 `server/src/index.js` 和 `auth.js` 读取 `Authorization: Bearer <token>`，令牌是 8 小时有效的 HMAC-SHA256 轻量令牌；每次受保护请求重新读取 `users.status`。当前没有 `x-token` 兼容逻辑、refresh cookie 或退出 API，前端退出只是清除本地存储。

因此当前 API 文档只记录 Bearer；HttpOnly、刷新令牌、限流和生产会话治理是后续安全工作，不得把旧 `x-token` 文本当作现行契约。

### 3.5 密码存储冲突：旧明文描述与当前 scrypt

`项目依据/01-project-design.md` 与 `06-review-gaps.md` 把早期演示登录描述为明文密码；当前源码使用 Node `crypto.scryptSync`、每次随机 16 字节盐和 64 字节摘要，保存为 `salt:hash`，测试已覆盖正确/错误密码验证。MySQL SQL 种子数据也使用该格式。

这只说明当前密码哈希实现已存在，不代表生产账号治理已完成：演示密码仍写在种子与文档中，尚无登录限流、强密码复杂度、刷新令牌、密钥管理和泄露后的轮换流程。

### 3.6 109 条 RTM 与当前源码证据冲突

RTM V1.1 在 Excel 中把页面、控件、预约、潮汐、膳食、情绪、指标、医护审核、服务人员视图等细化为 109 条，并且逐项跟踪列仍为 `×`。当前源码只覆盖一部分相邻展示和基础 API；没有为每条 RTM 提供实现、测试、评审证据。

因此本轮不把“页面看起来相似”“Agent 文案提到某能力”或“数据库设计预留字段”算作 RTM 通过。逐条现状映射见 [`API当前基线.md`](API当前基线.md)；状态只使用“部分覆盖”“范围不同”“未实现”，不使用 N/A 回避未完成项。

### 3.7 日期冲突：2026 文件名与 2025 Excel 序列

教学计划文件名为 `大工软院实习实训项目计划-2026_秋季（1-8）.xlsx`，但日期序列 `45901` 等按 Excel 日期解析实际落在 2025-09-01 至 2025-10-30。`项目依据/05-schedule-2026.md` 已按 2026-09-14 重新排期，但这不是原始教学文件的修改。两者必须同时保留：课程原始日期待指导教师确认，首轮开发排期采用交接/开发组织文档明确的 2026-09-22/23 上下文。

### 3.8 Word/PDF、交接和验收记录的证据边界

概要设计 Word 与 PDF 是同一版本（1.0.0，2026-09-19）的不同载体，章节内容基本一致，PDF 提取会出现页眉、分页和标题编号噪声；不能把两份载体当作两套独立通过结论。交接文档 Word 与 Markdown 的范围也基本一致，Markdown 便于开发阅读。

`验收记录/交付清单与SHA256.txt` 的 SHA-256 是打包时点记录，且说明当时保留了部分构建产物/旧锁文件；它不能替代当前 Git diff、npm 测试或构建结果。本轮 CI 不自动部署、不上传构建物、不读取密钥。

## 4. 当前首轮范围

### 4.1 快照中可作为“存在”的能力

以下只表示源码中有相应路径或演示行为，不表示满足早期业务验收条件：

1. 公开首页请求新闻列表/详情，展示预置新闻；天气卡是前端随机演示数据。
2. 客人、工作人员、院长使用用户名、密码、角色登录；Bearer HMAC 令牌有效期 8 小时，账号停用会在后续请求被拒绝。
3. 客人读取自己的档案摘要、最近健康记录和有效医嘱，页面可提交个人资料 PATCH 和修改密码。
4. 工作人员/院长可进入工作概览、客人列表、客人详情和建议发布；院长可查看工作人员记录并写院长意见。
5. Agent 有公开/客人/工作人员/院长提示词和规则降级；可选调用 OpenAI-compatible `/chat/completions`；客人健康关键词会写入简化的 `health_intakes` 原始文本。
6. 关键登录、查看客人、发布建议、院长意见和健康采集操作会写入当前 SQLite `audit_logs`（但日志脱敏、事务一致性和查询范围仍需治理）。

### 4.2 明确不属于当前首轮已完成的能力

疗程生成与版本历史、海滨项目库、潮汐/海况安全、预约容量与并发、每日简报、膳食点餐、心情/心理资源、手工指标录入与趋势、医护审核队列、分级审核、工作人员—客人分配、医护/管理员/服务人员权限、健康采集人工确认、正式 MySQL 迁移、生产模型治理和生产部署均不应标为已完成。
