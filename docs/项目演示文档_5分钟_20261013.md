# 海屿康养社区五分钟项目演示文档

核心流程与多智能体协作

演示版本：2026年10月13日本地工作区。适合项目汇报、课程展示或向非技术人员介绍，正文讲稿约5分钟，后面的功能清单和准备说明供演示者查阅。

这次用一位演示客人的经历串起来：先建立资料，让管家和四个专业智能体一起整理建议，再展示确认、日程、膳食和反馈入口。观众主要看懂一件事：客人说一次需求，系统怎样分工处理，以及建议怎样和实际服务衔接。

当前属于本地开发演示版。入口、资料和机构前置已有独立通过记录，四领域真实协作也已有运行实证；方案采纳和完整业务闭环仍在验收。演示时把已完成的协作结果与已准备好的业务记录分别展示，不说整套系统已经全部验收通过。

## 一 五分钟演示路线

| 时间 | 展示内容 | 观众要看懂什么 |
| --- | --- | --- |
| 0:00—0:20 | 首页与客人空间 | 这是给康养客人和工作人员共同使用的系统 |
| 0:20—0:55 | 我的档案与医护核实记录 | 建议会用到客人的资料，自述和正式档案有区别 |
| 0:55—2:55 | 管家对话与本次如何生成 | 四个专业智能体分工、查资料、给候选，再由管家汇总 |
| 2:55—3:30 | 候选状态与人工确认 | 可参考、已排除、待人工复核分别是什么意思 |
| 3:30—4:15 | 项目、日程和膳食 | 已确认的安排和订单能够在相应页面查看 |
| 4:15—4:45 | 打卡反馈、健康记录和心情 | 后续评估可以引用客人新记录的信息 |
| 4:45—5:00 | 机构工作区与收尾 | 医护和服务人员按自己的岗位接着处理 |

**时间安排：** 多智能体部分占2分钟。正式展示前准备好一次真实协作结果；现场可以展示提问内容，再展开已有结果。若现场发送新请求，等待超过15秒就切回准备好的记录，并说明这是此前真实运行保存的结果。

## 二 多智能体怎么分工

把它讲成“一个管家带着四个分工不同的帮手”即可。

| 角色 | 大白话职责 | 主要查看的资料 |
| --- | --- | --- |
| 海屿管家 | 接住需求、分配任务、汇总可以采用的候选 | 各专业任务结果和复核后的候选 |
| 理疗智能体 | 帮忙筛选温泉、海水浴、海泥等项目 | 项目介绍、健康约束、禁忌规则、理疗知识 |
| 营养智能体 | 帮忙看看三餐有哪些合适的选择 | 当天餐单、食材、过敏和忌口、营养知识 |
| 运动智能体 | 帮忙筛选轻松活动和可用时段 | 行动能力、项目、时段、已有安排、运动知识 |
| 心理陪伴智能体 | 帮忙选择可以使用的陪伴资源 | 心情记录、需人工关注的信息、陪伴课程 |

**协作顺序：** 客人提出需求 → 管家分派 → 专业智能体调用各自允许的资料工具 → 系统复核候选和限制 → 管家汇总 → 展示建议、来源和待处理事项。

多智能体可以使用同一个基础模型，重点在于任务、可查资料和运行记录分开管理。本项目已有真实模型参与四领域协作的记录；不能仅凭界面上的四个名字判断模型是否真的运行过。

## 三 可以直接照着讲的演示稿

只朗读“讲解”，操作提示供演示者自己看。角色切换、输入和页面加载都算在对应时间内。

### 1 项目开场

**时间：** 0:00—0:20。

**操作：** 打开首页，进入已经登录的客人空间。指一下“管家、日程、项目、膳食、我的”五个入口。

**讲解：**

> 大家好，这是海屿康养社区系统。我们用一位客人的经历来看：他来到社区后，系统怎么了解他的情况，怎么把理疗、吃饭、运动和心情陪伴几方面的建议整理到一起，再让工作人员接着处理。

### 2 先了解这位客人

**时间：** 0:20—0:55。

**操作：** 打开“我的 → 我的档案”，展示联系资料、健康自述和正式健康档案。医护核实过程优先用已经准备好的记录或机构页截图说明。

**讲解：**

> 先看这位客人的资料。联系信息可以维护，身体情况可以自己填写，比如行动能力、睡眠、过敏和饮食忌口。客人自己说的内容会先保留为自述，由负责的医护核实后更新正式档案。后面整理建议，就会用到这些资料。没有填写的项目，还需要继续确认。

### 3 重点展示四个智能体一起处理需求

**时间：** 0:55—2:55。

**操作：** 打开客人助手，展示一条同时涉及四个领域的提问。找到对应回复，点击“本次如何生成”，依次滚动展示海屿管家、四个专业任务、工具和引用，再展示“候选复核”。领域卡片有内部滚动区域，需要分别滚动。

**可复制的演示提问：**

> 我想了解温泉或海水浴，看看明天三餐吃什么，安排一点轻松的运动，再找一个舒缓心情的陪伴课程。请从理疗、营养、运动和心理陪伴四方面一起帮我整理建议，说明用到了哪些资料，未核实的信息请指出来。

这条提问用于触发四领域分工。演示以实际返回内容为准，不预先承诺某个项目一定可以参加。

**讲解：**

> 现在我们一次提出四方面的需求：水疗、三餐、轻松运动和心情陪伴。管家接到以后，会把任务分给四个专业帮手。
>
> 理疗智能体查看项目和禁忌，帮忙筛选温泉、海水浴这些选择；营养智能体查看餐单、食材和忌口；运动智能体查看行动能力、活动时段和已有安排；心理陪伴智能体查看心情记录和可用的陪伴课程。
>
> 点击“本次如何生成”，能看到每个任务的运行记录、调用过的资料工具和引用来源。这样我们知道，每个帮手具体做了什么，建议是从哪里来的。
>
> 它们先各自给出候选，系统再按规则复核，管家最后把可以采用的内容整理给客人。下面还能看到“可参考”“已排除”“待人工复核”。如果某个领域没有完成，也会保留缺口提示，方便继续处理。

**这两分钟必须展示的三处：** 四个专业任务名称；至少一处工具或引用来源；一处候选状态及其理由。运行编号、耗时和费用可以留在画面里，不用逐项朗读。若当前处于“安全引导模式”，应说明未调用真实模型，改为展示此前真实运行保存的协作记录。

### 4 建议怎样进入确认流程

**时间：** 2:55—3:30。

**操作：** 指向“可参考”“已排除”或“待人工复核”的真实条目及理由，再展示已有的助手确认卡或“等待医护审核”的草案。主线不要求点击新增的“采纳此方案”。

**讲解：**

> 这里的状态决定下一步怎么处理。可参考的建议，还要核对实际时段和条件；需要人工复核的内容，要交给工作人员。预约、点餐这些操作，系统已有让本人确认后再提交的入口；涉及健康风险的草案，还要经过医护审核。客人和工作人员都能看见当前停在哪一步。

**演示者备注：** 确认卡、普通草案与新增的四领域方案采纳是不同入口。当前“采纳此方案”已补入代码，尚未完成真实网页和数据库闭环验收，不能用其他流程的记录证明这条新链路已通过。

### 5 看看每天实际怎么用

**时间：** 3:30—4:15。

**操作：** 快速切到“项目”“日程”“膳食”。展示一个项目的实际时段、一条已有的成功预约，以及一份已保存餐单或订单状态。这个时段以查看为主。

**讲解：**

> 回到每天的使用。项目页能查看活动介绍、注意事项和时段余量；预约成功后，可以在日程里查到。膳食页可以查看当天餐单、过敏和忌口提示，也有点餐和订单状态。配餐员可以在自己的工作台查看订单，更新备餐和送达状态。客人能查到这些实际服务记录。

### 6 做完以后还能记反馈

**时间：** 4:15—4:45。

**操作：** 展示已有日程的打卡或感受反馈，再从“我的”进入“健康记录”或“心情与陪伴”。指一下“日程”中的“反馈后的疗程评估”入口即可。

**讲解：**

> 活动完成以后，可以打卡、记录感受。平时也能记录健康指标和今天的心情，使用陪伴资源。这些信息可以成为后续评估的依据。日程里已有反馈后再评估的入口，新产生的调整候选仍要按规则确认和审核。

### 7 机构接着处理

**时间：** 4:45—5:00。

**操作：** 展示准备好的机构工作区页面或截图，指一下“疗程审核”或“备餐工作台”。

**讲解：**

> 工作人员按岗位接着处理：医护核实资料、审核草案，服务人员查看自己的安排。多智能体负责分工整理，确认后的记录交给相应人员继续完成。

## 四 当前已实现的功能

以下是当前代码和已有记录能支持的功能范围。“已实现”表示已有对应页面或服务能力，各项完整业务验收状态仍有差别；五分钟主线只挑代表性页面展示。

| 功能 | 现在能做什么 | 演示范围 |
| --- | --- | --- |
| 首页与角色入口 | 公共介绍、新闻、客人注册登录、工作人员和院长登录 | 开场一带而过 |
| 客人资料 | 维护联系资料、填写健康自述、查看正式健康档案及来源版本 | 主线展示 |
| 入住与负责关系 | 机构登记入住和离店日期、安排负责工作人员 | 演示前准备，已有独立前置验收 |
| 医护核实与建议 | 负责医护确认或驳回自述，发布可追溯的医嘱和建议 | 用已有记录说明 |
| 智能管家 | 接收自然语言需求、分派专业任务、汇总候选；模型不可用时安全降级 | 主线重点 |
| 四领域协作与来源 | 理疗、营养、运动、心理陪伴分工；查看任务、工具、引用和候选状态 | 已有真实协作实证，主线展开轨迹 |
| 项目与环境信息 | 查项目介绍、禁忌、时段及环境快照；新增正常、风险、缺失、过期四种演示场景 | 合成环境需标明非实时、非机构批准 |
| 预约与日程 | 查询时段余量、预约、取消、查看日程；助手有本人确认卡 | 展示已有成功记录，提交仍复核条件 |
| 普通疗程草案 | 根据入住周期生成营养与运动草案，保留编号、版本、来源和审核状态 | 与四领域对话分开展示；完整本轮验收未通过 |
| 四领域候选采纳 | 新增“采纳此方案”，设计为沿用同一协作来源保存待审草案，防止重复提交 | 本地新增代码与定点测试已有，真实业务待验 |
| 疗程审核与历史 | 医护查看草案、修改、通过或退回，查询审核历史；生效时复核条件 | 用已准备好的页面说明，完整旅程待专项验收 |
| 每日膳食与配餐 | 生成并保存演示餐单、查看食材与忌口、点餐、查看订单、更新备餐和送达 | 菜品和供货为演示资料 |
| 健康记录 | 记录结构化指标、查看历史和趋势、保留来源 | 展示已有记录，不讲医疗判断 |
| 心情与陪伴 | 每天记录心情、查看近期变化、播放本地陪伴资源、记录使用 | 展示页面或短暂播放，不作心理诊断 |
| 打卡反馈与再评估 | 预约执行打卡、记录感受；用指标、心情、反馈来源形成调整候选 | 展示入口和已有记录，完整闭环仍须验收 |
| 机构与岗位管理 | 客人分工、员工账号、岗位权限、项目时段和容量维护、运营查询、服务日程、院长意见 | 五分钟只展示一个代表页面 |

## 五 演示前准备和当前边界

### 演示前准备

1. 提前启动本地演示环境，操作方法见同目录的《开发者启动手册》。使用隔离演示数据，先确认网页、登录和各页面能打开。
2. 准备一位虚构演示客人，已有有效入住日期、负责医护和实际核实记录；同时准备餐单、预约或反馈示例。按实际记录展示，不把未答字段补成“没有风险”。
3. 准备一次能看到四个专业任务的真实协作结果，并保存完整可读的备用截图或录屏。截图必须覆盖回复、来源、管家和每个领域的内部滚动内容，不能把已有的不完整截图说成全覆盖。
4. 演示前把客人页、医护页和备用画面放在方便切换的位置。收起可能遮住页面的浮动助手或播放器；预演时确认文字大小和滚动位置。
5. 环境四场景只在演示模式下展示。场景选择器目前只切换环境面板，未同步切换上方预约面板；不要用切换后的环境画面证明预约限制已经联动通过。
6. 完整试讲一次，把四领域协作稳定控制在2分钟左右。正文讲解约800字，其余时间留给点击、滚动和切页；不要把功能清单也逐行朗读。

### 当前需要如实说明的地方

**真实协作已经发生，全面验收仍未完成。** 最新第56轮记录证明同一会话中的四领域真实协作完成，但最终回复没有逐条列出六项未答资料：慢病史、长期用药说明、过敏源、饮食忌口、皮肤状况、客群标签；四领域内部滚动截图覆盖也没有通过。该轮整体仍为未最终接受，演示中不能说资料缺口提醒已经全部完善。

**方案采纳的代码和实际业务证据要分开。** 当前新增采纳入口及保存同一来源、保持待审核的逻辑已有代码和定点测试；第56轮没有实际点击采纳，未验证保存后回读。因此五分钟主线展示协作与已有业务页面，不把它们讲成已验收通过的同一条四领域落单链路。

**普通草案已有生成观察，完整包仍未通过。** 第54轮曾生成草案并留存刷新后的画面，但最终证据采集不完整，不能据此宣称全部来源绑定和业务检查已通过。普通生成主要调用营养和运动两个领域，不能拿它证明四领域候选采纳成功。

**数据与版本说清楚。** 四场景环境是合成演示，正常场景也不代表机构安全批准；菜单、供货和陪伴资源按本地演示范围介绍。采纳和环境四场景属于当前本地未提交修改，若换到远端主分支副本，需先核对是否具备相同功能。109项需求仍未全部验收，项目尚未宣称生产运营就绪。

### 现场遇到问题时怎么接

- 模型等待或服务不可用：说“这里切到此前真实运行保存的结果，继续看各个智能体怎样分工”，然后展示备用画面。
- 没有可参考候选：展示实际的“已排除”或“待人工复核”及原因，说明哪些条件还需要确认，不临时承诺能预约。
- 被问“能直接生成完整四领域方案吗”：说“目前四领域协作已经有真实记录，同一结果采纳成持久草案的入口刚补入代码，还在做完整业务验收。”
